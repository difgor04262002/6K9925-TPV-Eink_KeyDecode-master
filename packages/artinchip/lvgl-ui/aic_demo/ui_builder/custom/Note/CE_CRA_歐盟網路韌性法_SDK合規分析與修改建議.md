## 1. 結論先講：這顆產品現在差在哪

本專案是 **USB 連線的 TFT 顯示模組韌體**（WinUSB 複合裝置 + UART 指令 + 全碟 USB 升級），不是路由器、瀏覽器或作業系統套件。依執委會施行細則 (EU) 2025/2392「核心功能」判定，**極大機率屬預設類別（default）**，可走 Module A **自我評估**貼 CE；不需要先排隊 Notified Body。這是好消息。

壞消息是：預設類別仍必須滿足 CRA **附件一**，並且要能拿出附件七技術文件。以本 SDK **今天的實作**來看，最大缺口不是「沒寫 DoC」，而是韌體本身：

| 嚴重度 | 缺口 | 為什麼 CRA 會卡住 |
|--------|------|-------------------|
| **P0** | USB／UART 上的 **9-byte BROM 觸發**即可進入全碟燒錄，無認證 | 任何人接上 USB 就能改寫整顆 SPI NAND（附件一：未授權存取、安全更新） |
| **P0** | `image_authentication()` **固定回傳 0**（RSA 欄位形同關閉） | 升級只靠 checksum，惡意 `.img` 可被寫入 |
| **P0** | **沒有 SBOM**、沒有弱點監控 | 2026-09-11 起連「該不該通報」都無法判斷；既有市售品也適用第 14 條 |
| **P1** | 量產映像開 **UART0 tshell／MSH**、完整 log | 除錯介面等於未上鎖的管理面（secure by default） |
| **P1** | 版本識別分裂：SDK `v1.2.2`、`image_cfg.json` `1.0.0`、面板 `V0.0.49` | 附件七要求「影響合規的軟體版本」可追溯 |
| **P1** | 無支援期政策、無公開弱點窗口（`security.txt`／security@） | 附件二使用者資訊、附件七 §2(b) |
| **P2** | 第三方元件（RT-Thread、LVGL、CherryUSB、FatFs、NFTL）未列管 | 上游 CVE 無法對到出貨版本 |
| **P2** | USB 顯示串流無完整性／來源驗證 | 屬功能面；若產品宣稱「僅信任主機」需寫進風險評估而非 silently 假設 |

**一句話**：若產品**已經或即將**在歐盟販售，2026-09-11 前至少要完成 **SBOM + 弱點窗口 + 通報 SOP**；2027-12-11 前出貨的每一台新裝置，還必須把 **安全更新（簽章）** 與 **除錯介面關閉／上鎖** 做進韌體，否則沒有合格 CE。

## 2. 產品與法規對位

### 2.1 本專案是不是 CRA 的「具數位元件產品」？

是。CRA 涵蓋硬體、韌體、軟體，以及獨立販售的純軟體。本產品包含：

| 層 | 本專案對應 | 可否更新 |
|----|------------|----------|
| SoC Mask ROM（BROM） | ArtInChip D21x Boot ROM | 否（出廠焊死） |
| SPL／tinySPL | `application/baremetal/bootloader` | 是（`spl` 分區） |
| Application | RT-Thread + LVGL UI（`custom/`） | 是（`os`／`rodata`／`data`） |
| 面板／觸控 FW | ST7121P／ST7123 等（模組內） | 通常由面板廠維護；仍須列入 SBOM／供應商條款 |
| 主機端工具 | `upgcmd`、AiBurn、USB Display 協定 | 若一併提供給歐盟客戶，也算數位元件 |

2027-12-11 之後「投放市場」的**每一台新裝置**都要符合；同型號舊庫存在該日後出貨歐盟也算新投放。已在市場上的個別裝置不必回溯完整 CRA，但 **2026-09-11 起的弱點／嚴重事故通報仍適用**。

### 2.2 製造商是誰？

CRA 義務最重的是「製造商」（把自己的名字／商標放到產品上、投放市場的那一方）。

| 出貨模式 | 誰扛 CRA | 本 SDK 要配合什麼 |
|----------|----------|-------------------|
| ENE 自有品牌外銷歐盟 | ENE 是製造商 | 本文件全部適用；需歐盟授權代表持有技術文件 |
| 白牌／ODM 貼客戶品牌 | **品牌方**是製造商，ENE 是供應鏈 | 仍須提供 SBOM、簽章金鑰交付、弱點通知、支援期承諾給品牌方，否則客戶無法過 CE |
| 只賣模組給系統廠 | 系統廠可能是製造商 | 模組仍是「數位元件」；合約要規定安全更新與 SBOM 交付 |

無歐盟據點時，應指定 **Authorised Representative** 持有技術文件、對接市場監督機關。

### 2.3 產品類別（決定能不能自我評估）

依 [ICSDA 文](https://icsda.org.tw/%e8%b3%87%e5%ae%89%e7%9f%a5%e8%ad%98%ef%bd%9cce-%e6%a8%99%e7%ab%a0-x-%e6%ad%90%e7%9b%9f-cra%ef%bc%9a%e5%8f%b0%e7%81%a3%e4%bc%81%e6%a5%ad%e7%9a%84%e5%90%88%e8%a6%8f%e6%99%82%e9%96%93%e8%bb%b8/) 與 (EU) 2025/2392：分類看**核心功能**，不看商品名。

| 類別 | 例子 | 本產品？ |
|------|------|----------|
| 預設（約 90%） | 一般連網／USB 裝置 | **預設判定：是**（USB 顯示模組） |
| 重要 Class I | OS、路由器、VPN、瀏覽器、智慧鎖／攝影機等 | 否（本核心功能是顯示＋觸控，不是網路邊界或身分管理） |
| 重要 Class II／關鍵 | 防火牆、Hypervisor、電表閘道、安全元件 | 否 |

**注意**：本板 defconfig **未把 Wi-Fi 當產品核心功能啟用**（應用側是 USB Device + UART）。若未來量產 SKU 加上無線並「供上網連線」，可能接近 Class I「路由器／數據機／交換器」或 RED DA（無線電）範圍，須重新判定。**有無線的 SKU 現在就適用 RED Delegated Regulation (EU) 2022/30／EN 18031**（2025-08-01 已強制）。純 USB 有線模組則 RED DA 通常不適用。

調和標準（EN 40000 系列）截至 2026-07 **尚未刊登 OJEU**，因此還不能主張第 27 條「符合性推定」。預設類別本來就可自評，但要**自行舉證**如何滿足附件一（可用 IEC 62443-4-1/-4-2、ETSI EN 303 645 當替代方案寫進附件七 §5）。

### 2.4 罰則（提醒決策層）

- 違反附件一或第 13、14 條核心義務：最高 **1,500 萬歐元或全球年營業額 2.5%**（取高）
- 技術文件／CE 標示等：最高 1,000 萬歐元或 2%
- 通報義務從 2026-09-11 起算，且含**當時已在歐盟市場的產品**

過渡條款（第 69 條）三句話：

1. 2027-12-11 **前**已投放的個別裝置，不必回頭符合完整 CRA。  
2. **通報是例外**：2026-09-11 起既有市售也要通報。  
3. 「重大修改」（改架構、加功能、影響基本要求）視同新投放；**單純安全修補通常不算**重大修改。

對本 SDK 的實務解讀：現在出貨的 v1.2.2／image 1.0.0 若已在歐盟，9 月起要能監控與通報；若 2027 年底前要加「簽章升級、關 shell、改 USB 協定」這類**安全修補**，應規劃成不改變預期用途的更新，避免被認定為重大修改卻沒做完整符合性評估。建議法務把「安全更新範圍」寫進變更管制。

## 4. 現況盤點（對照本 SDK 實際程式）

### 4.1 已具備、可當成符合性證據「胚」

這些不是「已符合 CRA」，但寫技術文件時可以當起點：

| 現況 | 位置 | 可轉用的證據 |
|------|------|----------------|
| 開機列印 SDK 與映像版本 | `kernel/rt-thread/src/kservice.c`：`ENE Tech Inc. v1.2.2 [6K9901]`、`Image version`、`Built on` | 附件七 §1(b) 版本識別的雛形 |
| 映像 checksum（CRC32／加總） | SPL `image_verify_checksum()`；log 有 `CRC32 verify OK` | 完整性檢查的一部分，**不足以**當認證 |
| 映像頭已預留 RSA2048 欄位 | `bsp/common/include/aic_image.h`：`AIC_FW_SIGN_ALGO_RSA2048` | 附件一「安全更新」的**現成鉤子** |
| 硬體看門狗 | `CONFIG_AIC_USING_WDT`、freeze watchdog | 可用性／卡死恢復（非資安主軸，但可寫入風險處置） |
| 重置原因紀錄 | WRI／`aic_get_reboot_reason()` | 事故調查日誌的硬體基礎 |
| USB 升級狀態機文件化 | `Note/Luban-Lite_燒錄IMG完整說明.md`、`upgcmd_燒錄工具使用說明.md` | 附件七 §2(c) 生產／更新流程說明草稿 |
| Git 版本庫 | GitHub `Luban-Lite_RTOS_SDK_D215-master` | 變更追溯；**還不是** SBOM |
| 面板／觸控驅動有獨立版號 | 例：H0499 `H0499_DRIVER_VERSION` | 元件版號，應納入 SBOM |

### 4.2 明確不符合或高風險的實作

#### （1）未認證即可進入全碟升級

`packages/artinchip/lvgl-ui/aic_demo/ui_builder/custom/custom.c`：

- 固定 9-byte：`FF A1 B2 E3 F4 C5 D6 EE EE`
- USB bulk OUT 整包相符或 UART 逐 byte 拼湊命中 → `custom_trigger_brom_mode()`
- 設 reboot reason + 停踢 WDT → 進 UPGMODE → `upgcmd image` 可重寫 `spl`／`os`／`rodata`／`data`

這在開發上很方便，在 CRA 上等於 **未授權行為者只要能跟裝置說話就能改韌體**。主機端 Display 協定與升級觸發走同一條 WinUSB bulk。

#### （2）簽章驗證是空函式

```c
/* application/baremetal/bootloader/lib/common/image.c */
int image_authentication(u8 *fw_base)
{
    return 0;   /* 永遠成功 */
}
```

標頭允許 `sign_algo = RSA2048`，HAL 也有 `RSA2048_SIGN_LEN`，但 SPL **沒有驗證**。攻擊者改 checksum 欄位即可過關。

#### （3）除錯面預設開啟

- UART0：`CONFIG_RT_CONSOLE_DEVICE_NAME="uart0"`，RT-Thread MSH／tshell（log 可見 `aic />`）
- 可下系統指令、看記憶體、觸發升級相關命令（視編譯選項）
- 量產若未關 console，等於實體／線纜攻擊面常開

#### （4）USB／UART 應用協定無來源認證

`custom_recv_18bytes` 路徑接受主機 AA／CD 指令與圖檔串流。產品若接在不可信 USB 主機（共用 PC、惡意充電線轉接），可：

- 觸發 BROM
- 塞異常圖檔（可用性；需威脅模型決定是否列資安）
- 無 TLS／無挑戰回應（裝置是 USB device，通常不做 TLS，應改用 **訊息簽章或配對金鑰**）

#### （5）第三方元件未盤點

實際會進 6K9901 映像的至少包括：

| 元件 | 典型來源 | 授權（需核對實際檔頭） |
|------|----------|------------------------|
| RT-Thread | `kernel/rt-thread` | Apache-2.0 等 |
| ArtInChip HAL／BSP | `bsp/artinchip` | Apache-2.0 |
| LVGL v9 | `packages/artinchip/lvgl-ui/lvgl_v9` | MIT |
| CherryUSB | `packages/third-party/cherryusb` | Apache-2.0 |
| FatFs（elm） | DFS elmfat | BSD-style |
| NFTL／ramdisk | `packages/third-party` | 專案授權 |
| ST7123 驅動 | `bsp/peripheral/touch/st7123` | 專案 |
| 面板 init（H0499 vendor DCS） | `panel_h0499s010_init` | 面板廠／ENE |
| 字型／圖檔 | `rodata/lvgl_data` | 授權須單獨清（TTF 授權常被忽略） |

目前 **沒有 CycloneDX／SPDX**，也沒有 CI 在每次 build 產出 SBOM。

#### （6）版本線不一致

| 識別 | 現值（2026-08 實機） | 問題 |
|------|----------------------|------|
| SDK banner | `v1.2.2`（`LL_VERSION` 寫死） | 與 Git commit、image 1.0.0 無強制連動 |
| `image_cfg.json` | `"version": "1.0.0"` | 燒錄映像對外版本 |
| 面板驅動 | `V0.0.49` | 只在 UART log |
| USB bcdDevice | `0x0001` | 主機端幾乎看不出韌體世代 |
| Git | `f622b974` 等 | 未寫入裝置 |

附件七要求：哪個韌體版本對應哪份技術文件。現在稽核員問「歐盟那批貨是哪一版」，對不到單一識別碼。

## 5. 附件一差距：產品資安要求（Part I）

下列用工程語言對應 CRA 附件一 Part I 常見要求（secure by design／default）。完整法條請以 EUR-Lex 為準。

| 要求（意旨） | 本 SDK 現況 | 建議改法（見第 7 節編號） |
|--------------|-------------|---------------------------|
| 在設計上消除已知漏洞、最小攻擊面 | USB 升級＋shell＋明文協定全開 | M1、M3、M4 |
| 安全預設設定 | 開發設定即量產設定 | M3：量產 defconfig 關 MSH、降 log |
| 保護未授權存取 | BROM 9-byte 公開且固定 | M1 |
| 機密性／完整性（傳輸與儲存） | 韌體無簽章；USB 無完整性 | M2、M5 |
| 安全更新（可安裝、可驗證、支援期內免費） | 有 USB 全碟更新，**不可驗證來源** | M2、P-SUP |
| 弱點處理機制 | 無 PSIRT、無 SBOM | M6、P-CVD |
| 限制攻擊面／關閉不必要介面 | UART0、UART5、USB、SD 熱插拔 | M3、M7 |
| 記錄與監控安全相關事件 | 有 UART log，無安全事件環形緩衝／不可否認 | M8 |
| 復原能力 | WDT 可復原 hang；升級失敗依賴人工 | M2 加 A/B（分區已有 `os_r`／`rodata_r` 未當回滾用） |

**A/B 分區是隱藏優勢**：`image_cfg.json` 已有 `os_r`、`rodata_r`、`data_r`。CRA「更新失敗可恢復」可走 **未驗證成功不切 boot 槽**，不必重做 Flash 配置。目前實際升級是 UPGMODE 全碟覆寫，失敗可能變磚，需人工再燒。這應列入風險評估，並排程改成「驗證簽章 → 寫入備用槽 → 確認開機 → 切換」。

## 6. 附件一差距：弱點處理要求（Part II）

Part II 是**常態義務**（所有弱點都要處理），第 14 條通報只針對「遭積極利用」與「嚴重事故」。

## 7. SDK／韌體建議修改清單（可執行）

以下「M」＝韌體／SDK 修改；「P」＝流程與文件（不一定改 C 程式）。**不要一次全做**；優先序見第 11 節。

### M1 — 升級觸發認證（P0，改 `custom.c`）

**問題**：固定 9-byte 等於公開後門。

**建議作法（由易到難）**：

1. **短期（仍給產線用）**  
   - 量產韌體：**預設關閉** UART／USB 的 BROM pattern。  
   - 僅在 GPIO 進位、OTP 熔絲「工廠模式」、或開機後 N 秒視窗內接受。  
   - 開發 defconfig 另開 `CONFIG_ENE_FACTORY_UPG_TRIGGER`。

2. **中期（建議量產）**  
   - 觸發改為：主機送 `challenge` ← 裝置亂數；主機用 **HMAC-SHA256（裝置唯一金鑰）** 回 `response`。  
   - 金鑰寫在 OTP／eFuse 或出廠注入的 `env`（不可出現在 Git）。  
   - 失敗次數限制＋冷卻，防止 USB 爆破。

3. **與 upgcmd 的關係**  
   - BROM／SPL 的 ArtInChip 協定可能仍無認證（SoC 限制）。CRA 風險評估可寫：「實體 USB 在可信產線／授權維修點」；**應用階段不得再提供零認證跳 BROM**。  
   - 若維修必須遠端升級，走 M2 簽章映像，而不是 9-byte 魔術值。

**測試**：惡意 PC 只送 9-byte → 量產機**不得**進 UPGMODE；工廠治具走金鑰或硬體按鍵仍可燒。

### M2 — 啟用映像簽章驗證（P0，改 SPL + 打包）

**問題**：`image_authentication()` 空實作。

**建議作法**：

1. 啟用 ArtInChip 既有 RSA2048 路徑（`AIC_FW_SIGN_ALGO_RSA2048`），公鑰放 SPL 或 OTP。  
2. `mk_image.py`／打包腳本：CI 用**離線 HSM 或受控私鑰**簽 `d21x_os.itb`、`bootloader.aic`。私鑰不進 Git。  
3. SPL 載入 OS 前：magic → checksum → **RSA 驗簽**，失敗則不跳轉、必要時回 `os_r`。  
4. UPGMODE 寫入前同樣驗簽，拒絕未簽名／錯鑰映像。  
5. 金鑰週期與撤銷：技術文件寫「金鑰識別、輪替、舊版是否仍接受」。

**對應 CRA**：安全更新可驗證來源與完整性；附件七 §6 可附「未簽名映像被拒」測試報告。

### M3 — 量產組態：關除錯面（P1，改 defconfig）

建議拆兩套：

| 項目 | 開發 `*_defconfig` | 量產 `*_release_defconfig`（新） |
|------|-------------------|----------------------------------|
| `RT_USING_FINSH`／MSH | 開 | **關** |
| UART0 console | 開 | 關或只留 panic 最短字串 |
| log 等級 | I/D | E only |
| BROM 9-byte | 可開 | 關（M1） |
| USB VID/PID／bcdDevice | 可同 | bcdDevice 對應真實版本 |
| WDT | 開 | 開（維持） |

另：評估 UART5 自訂協定是否只應在「已配對主機」出現。

### M4 — USB 裝置識別與最小權限（P1）

- `bcdDevice`／字串描述符帶 **可解析的韌體版本**（對應 `image_cfg.json` version）。  
- 評估 WinUSB 是否需拆「顯示介面」與「維護介面」；維護介面僅授權工具能開（主機端用 WinUSB + 簽章指令）。  
- 補齊／修正描述符（現有 log 曾出現 `descriptor type 0x03 index 0x03 not found`），減少異常列舉與相容性事故（可用性，可寫風險評估）。

### M5 — 應用協定完整性（P2）

AA／CD 圖檔協定可分階段：

1. 先做 **長度／CRC／最大尺寸** 嚴格檢查（防畸形封包）。  
2. 再做 **工作階段 MAC**（與 M1 同一裝置金鑰）。  
3. 不要為了 CRA 去上 TLS（USB device 不適）；風險評估寫清「信任模型＝授權主機」。

### M6 — 建置時產出 SBOM（P0 流程，改 CI／打包）

每次正式發版（`mk_image.py` 之後）產出：

- CycloneDX 1.6 或 SPDX 2.3（機器可讀）  
- 至少涵蓋：RT-Thread、LVGL、CherryUSB、FatFs、本倉庫 commit、編譯器版本、`image version`、面板驅動版號  
- 與 `d21x_*.img` **同一版本號綁定**，存 10 年或至支援期結束（取長）

可用 cdxgen／syft 掃原始碼樹，再**人工補**嵌入式閉源（面板 init、NFTL lib）。ICSDA 文亦提到嵌入式 C/C++ 常漏列 Linux／OpenSSL／BusyBox——本產品無 Linux 使用者空間，但 **RT-Thread + CherryUSB + LVGL** 同等級必須列。

建議目錄（發版產物，不必進 Git LFS 也可放發行區）：

```
release/<image-version>/
  d21x_....img
  sbom.cdx.json
  sbom.spdx.json
  vex.cdx.json          # 弱點處置（受影響／不受影響＋理由）
  git-rev.txt
```

### M7 — 關閉或鎖定未使用介面（P2）

盤點 dacai03：USB Device、UART0、UART5、SDMC1（log 有 `/sdcard` mount fail）、QSPI NAND。  

- 量產若無 SD 卡功能：關 SDMC 驅動，減少惡意外接儲存。  
- 無線相關套件不要連進此 SKU。  
- USB 升級以外的 `upgcmd shcmd` 僅 SPL 存在；量產 SPL 應關危險 shell 或加密語（若晶片／SDK 支援）。

### M8 — 安全事件紀錄（P2）

至少在 `data` 分區保留 ring buffer（掉電可保存更佳）：

- 升級嘗試：成功／失敗／簽章失敗／觸發來源（USB／UART／按鍵）  
- WDT 復位原因  
- 連續認證失敗  

供第 14 條「知悉」起算與結案報告用。現有 UART log **不能**當唯一證據（客戶端沒接 UART）。

### M9 — 版本單一真相來源（P1）

建議：

1. `image_cfg.json` `version` 為**對外版本**（語意化：MAJOR.MINOR.PATCH）。  
2. 編譯時寫入 `os`：banner、USB bcdDevice、一個可被主機讀的 USB/UART 指令「GET_VERSION」。  
3. `LL_VERSION` 可保留 SDK 基底版，但必須另印 `ENE_FW_VERSION`。  
4. 變更管制：安全修補只加 PATCH；加功能加 MINOR（可能構成重大修改，需法務看）。

## 9. 弱點通報流程（2026-09-11 起）

### 9.1 先分清「處理」與「通報」

- **處理**（Part II）：研究者回報、掃描到的 CVE、上游 CherryUSB／LVGL 公告 → 一律走內部流程。  
- **通報**（第 14 條，ENISA SRP）：僅當  
  1. **遭積極利用的弱點**（有實際攻擊證據，例如 KEV／實網利用本產品），或  
  2. **嚴重事故**（影響產品安全性的重大事件）。  

一般「GitHub 上 CherryUSB 新 CVE、尚無利用本裝置的證據」→ **不必** 24h 通報，但要分析、VEX、排修補。

### 9.2 建議內部流程（對準本產品）

```
接收（security@／客戶／上游／NVD）
  → 用該版 SBOM 對元件與「哪些 image version／哪些 PID SKU」
  → 驗證是否可在 6K9901 上利用（USB bulk？shell？簽章繞過？）
  → VEX：受影響／不受影響＋理由
  → 是否積極利用或嚴重事故？
        是 → 知悉當下起算 24h 預警／72h 正式／修補後 14d 結案（SRP）
        否 → 排程簽章更新、安全公告、通知授權客戶
  → 證據寫入技術文件
```

「知悉」就起算，不是「分析完」才起算。因此要先有值班與草稿欄位，不能等 9/11 當天現編。

### 9.3 本產品較可能的通報情境（演練題）

1. 公開的 BROM 9-byte 被寫進利用工具，客戶現場裝置被刷惡意韌體。  
2. 未簽章升級被中間人（惡意 PC）寫入。  
3. CherryUSB／WinUSB 描述符解析漏洞導致異常（視嚴重度）。  

演練時用 M8 日誌證明「何時知悉、刷了哪一版」。

## 10. 建議不要立刻大改的項目

這些**不要**為了「看起來很 CRA」而在顯示尚未穩定時硬做：

| 項目 | 原因 |
|------|------|
| 自行實作完整 Linux 式安全開機鏈（TEE／measured boot） | SoC 能力與時程；先把 RSA 映像驗簽做對就有附件一主證據 |
| USB 上 TLS | 架構不合；改 HMAC／簽章即可 |
| 把產品自我升級成 Class I「安全裝置」行銷 | 可能被迫走第三方驗證 |
| 一次重寫 USB 顯示協定 | 主機生態相容性；先關升級後門、再漸進加 MAC |
| 為 H0499 暖開機沒畫面而引入未經驗證的電源時序當「資安修補」 | 那是品質／可用性；可寫風險評估「需斷電恢復」，與 CRA 弱點分開追蹤 |
| 把 ConEmu 歷史、output 目錄當 SBOM | 無意義且有雜訊 |

顯示／觸控（H0499 V0.0.49 RESX、ST7123）繼續走原工程追蹤，**不要**和 CE／CRA 文件綁成同一個里程碑，以免合規與出畫互相卡關。
